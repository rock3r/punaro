# Executive summary — Punaro indirect Internet deployment

**Recommendation:** adopt a Cloudflare-first hybrid deployment. Use Cloudflare Tunnel + Cloudflare Access for normal laptop and unattended native-client access, and a narrowly scoped public Remote MCP/OAuth surface for web-hosted ChatGPT and Claude. Also support Tailscale as a peer-selected private-native route for people who operate a tailnet. Do not make Punaro’s listener, LAN HTTP profile, database, health endpoint, or administrative services public.

This preserves the existing security model: native clients still require their distinct Punaro device credentials or signed machine requests, and every operation remains subject to server-side project capabilities. Browser/session Cloudflare Access is an additional admission boundary for the native hostname. A separate Access application may authenticate the human operator at a dedicated OAuth consent UI, but it is not a project grant and does not protect MCP discovery, OAuth protocol endpoints, callbacks, or background tool calls.

The core reason is interoperability. Claude says its remote MCP traffic originates from Anthropic cloud infrastructure and requires a public endpoint. ChatGPT now documents a distinct Secure MCP Tunnel for private developer-mode connections: an operator-run client makes outbound HTTPS requests to OpenAI and forwards MCP locally. Neither product joins a tailnet, runs `cloudflared`, supplies arbitrary Access service-token headers, or sustains an Access browser session on background calls. Cloudflare Access OAuth is a genuine standards-based admission option, but its token cannot be assumed to satisfy Punaro’s JWT/project-grant contract; any use requires an explicit non-bypassable exchange. The authoritative control remains Punaro OAuth plus subject/project capabilities—not network admission.

The **edge-unauthenticated hosted protocol surface** reachable via Tunnel should be limited to:

- Remote MCP `/mcp` and its OAuth protected-resource metadata.
- OAuth authorization-server metadata and JWKS.
- The minimal OAuth authorization, token, and revocation endpoints.

Two additional hostnames are publicly network-reachable but Access-gated: the exact qualified native route families at `cli.` and the separately-audienced human consent UI at `consent.`. They are not edge-unauthenticated application surfaces, and Access admission never replaces Punaro authentication or project authority.

Everything else remains loopback- or private-access-only: health/readiness, metrics, PostgreSQL, blobs, backups, owner/admin operations, enrollment issuance, relay management, and Tailscale Serve when a peer selects that route. Strict single-use enrollment redemption remains available on the dedicated `cli.` Tunnel + Access boundary so a new laptop can enroll; all other native device calls still require their own device credential or signed machine request. Native route families are published only after authenticated ingress proof, and legacy relay routes additionally wait for Punaro’s closed public-relay/operations release gate. The Tailscale route carries the same application identity/capabilities and never exposes raw LAN HTTP. Tailscale Funnel is expressly rejected because it is Internet-public.

The repository already has useful foundations—loopback ingress policy, device enrollment, signed requests, capabilities, body-free audit posture, native protected credential profiles, separate health listener, and remote-MCP metadata/token validation gates. It does **not** yet have a mounted remote-MCP transport/tools, OAuth authorization server and explicit browser-operator identity, durable immediately revocable subject/project grants, a read-only default scope, authenticated route-specific ingress proof, hardened deployment proof, or signed client distribution. Those are blockers, not documentation gaps.

Implementation should proceed only as independently reviewed milestones: authenticated ingress and origin hardening with no hostname yet published; Cloudflare Access native bootstrap and the optional Tailscale route; separately qualified native application families; OAuth-compatible Remote MCP with the existing black-box E2E suite extended; ChatGPT validation; Claude validation; revocation/incident drills; then signed distribution. Each must prove external origin isolation, generic errors, no secret/body logging, immediate durable revocation, exact token-format/audience checks, and least-privilege project capability enforcement. The initial hosted surface is `memory.search`/`memory.read`; current default `memory.propose` must not be exposed until separately consented.

For the two-vendor objective, Cloudflare remains the recommended common MCP edge because Claude still requires it. Before enabling ChatGPT, pilot OpenAI Secure MCP Tunnel as an optional hardening profile. It can remove ChatGPT from the public Cloudflare MCP route and allow that route to be narrowed to Claude’s documented source ranges, but it adds a second tunnel binary, runtime API key, RBAC/workspace association, monitoring path, and outage domain. The current official ChatGPT and Claude setup pages do not publish stable OAuth callback URLs; exact values must be captured from each product during disposable validation and registered without wildcards, or that client is no-go.

The full architecture, endpoint matrix, trust diagrams, exact compatibility tests, threat model, operational topology, and go/no-go checklist are in [the design document](indirect-internet-deployment-design.md).
